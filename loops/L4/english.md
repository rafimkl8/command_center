# L4 — English track

Written from memory, in my own words, self-corrected across review where wrong.

**Decorators, wrapping, and @ syntax (final, corrected version):**
> Decorator is a shape of function. It must have a wrapper inside it. The wrapper takes values in *args and **kwargs because it doesn't know from before what's going to be passed inside it. Inside the wrapper, the values or any calculation needs to be returned, otherwise it will show None without the return statement. It works exactly like closure, the wrapper keeps a live reference into the outer function's own private scope. The argument lives inside the scope, even after the outer function finishes. @ is shorthand for name = decorator(name).

**What was wrong in earlier passes (self-corrected during review, not by having it rewritten for me):**
- Blank page had no real mechanism at all: a decorator was described as something that "wraps up a function using @", `@` itself was described as "annoints to the function it's referring to", and wrapping was defined circularly as "the function is held by @_____, around it" — none of these said what actually happens, only what it looks like.
- First correction needed: `@` is not a blessing or attachment on the function — it is shorthand for reassigning a name. `@my_decorator` above `def target():` is exactly `target = decorator(target)`, run immediately after the `def` block.
- A related misconception surfaced and was corrected mid-session: claiming `@my_decorator` "turns say_hi into a wrapper" implies the decorator rewrites the function's own source code. It doesn't — the original function's body is never touched. Only the *name* gets reassigned to point at a different function object; the original still exists, unedited, trapped inside the closure.
- The closure explanation for *why* the wrapper still has access to the original function after the outer function has finished running was, on the first two attempts, described as "it remembers the value" / "keeps a copy... in the local scope" — the same imprecise, copy/memory framing L3 had already corrected once. Rewritten to the accurate mechanism: the wrapper keeps a *live reference* into the outer function's own private scope from that specific call, not an independent copy — which is also why two separate calls to a decorator-maker don't interfere with each other.
- The print-vs-return distinction from L1 resurfaced twice in this loop: once claiming a no-return function "produces the stored value" (nothing is stored anywhere — it's `None`, full stop), and once claiming a dropped `return` inside `wrapper` would give `None` "because nothing get's printed" rather than because there was no return statement. Both corrected to: printing and returning are unrelated; a function with no `return` always evaluates to `None`, regardless of what it printed along the way.
- `*args`/`**kwargs` in `wrapper`'s own definition was first described as "unpacks the values" — that's the call-site operation. In the `def` line itself it's the opposite: it *packs/collects* whatever gets passed into a tuple/dict; unpacking happens separately, at the point `wrapper` calls the original function back out again.
